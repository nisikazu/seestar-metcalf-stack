# メジアンスタック行分割ベンチマーク

測定日: 2026-09-01

## 測定条件

同じ220P/McNaughtのセッション2、247枚、RGB、1920×1080のサブフレームを使用した。
エフェメリス、WCS、メジアン方式を揃え、行分割数だけを変更した。行分割数の差を明確に
するため、比較本体では`--stack-workers 1`に固定した。

「分割なし」は1920行を1タイルで処理する設定である。分割数2、4、8、16はそれぞれ960、
480、240、120行の全幅タイルになる。

## 行分割数による比較

| 分割 | 1タイルの行数 | タイル数 | スタック時間 | 全工程 | Python Peak RSS |
|---:|---:|---:|---:|---:|---:|
| なし | 1920 | 1 | 542.13秒 | 595.75秒 | 8321.7 MiB |
| 2 | 960 | 2 | **410.07秒** | **465.28秒** | 6249.3 MiB |
| 4 | 480 | 4 | 499.35秒 | 557.57秒 | 3296.9 MiB |
| 8 | 240 | 8 | 726.96秒 | 777.54秒 | 1822.3 MiB |
| 16 | 120 | 16 | 1163.54秒 | 1214.99秒 | 1091.6 MiB |

全工程時間には共通の前処理とSirilによる星登録を含む。スタック時間は中央値の作業
キューブ作成から出力生成までの時間である。

2分割が最速で、分割なしと比べてスタック時間は24.4%、全工程は21.9%短縮した。分割なし
では大きな作業キューブによるメモリ圧迫が発生した。一方、4分割以上では各タイルで247枚
すべてを再読込するI/OとFITSデコードのコストが大きくなり、分割数を増やすほど遅くなった。

メモリ使用量は分割数を増やすほど減少する。8分割・16分割は速度向上のためではなく、
メモリの少ないPCで処理を完走させるための設定である。

## 正しさ

5条件のメトカーフ出力FITSはすべて同じSHA-256になった。

`5D101C669F4FFB22C10AD16C84A8071591BF915CC0968885C7C88B32AF9B56F4`

全条件で247枚を処理し、タイル割り当てのフォールバックは発生しなかった。分割によって
出力の画素値や有効領域が変わることは確認されなかった。

## 実用上の結論

通常は`--median-tile-rows auto`を推奨する。空きRAMから安全な作業キューブサイズを自動
決定するため、PCごとに適切な行数が変わる。

この測定環境で明示的に指定するなら、速度とメモリのバランスは2分割
（`--median-tile-rows 960`）が最も良かった。RAMが少ない場合は4、8、16分割を選べるが、
分割数を増やすほど処理時間は長くなる。

測定生データは`metcalf_output/median-tile-benchmark-20260901/benchmark-summary.csv`と
`output-hashes.csv`に保存している。

## 新版production codeのauto再測定

同じ新版production codeを、`--stack-workers auto`と
`--median-tile-rows auto`の既定値で再測定した。実行時の空きRAMにより、autoは
640行×3タイル、4 workerを選択した。

| 項目 | 新版auto実測値 |
|---|---:|
| 採用枚数 | 247/247枚 |
| タイル | 640行×3 |
| worker | auto選択の4 |
| スタック時間 | 257.83秒 |
| 全工程 | 336.23秒 |
| Python Peak RSS | 4671.6 MiB（約4.56 GiB） |
| タイル割り当てフォールバック | 0 |

前回のauto実測（720行×3タイル、スタック215.55秒、全工程268.47秒）より遅くなったが、
autoが参照した空きRAM、OSのファイルキャッシュ、バックグラウンド負荷が異なるため、
この差だけでタイルサイズの優劣は判断しない。今回の明示指定比較では、2分割が最速で、
autoはPCの空きRAMに応じて安全側の行数を選ぶ設計である。
