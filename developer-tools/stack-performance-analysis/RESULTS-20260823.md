# Stack performance and temporary-storage analysis: 2026-08-23

## Scope

The initial measurements used retained registered frames from the
220P/McNaught session. Each registered RGB float32 FITS is 24,888,960 bytes.
Those tests established numerical agreement before production integration;
the final production implementation and end-to-end measurements are recorded
below.

## Per-frame measurements

Representative warm-cache timings were:

| Operation | Current | Prototype | Change |
| --- | ---: | ---: | ---: |
| FITS read | 0.02-0.07 s | unchanged | not a primary bottleneck |
| Quadratic background fit | 0.14-0.17 s | unchanged | modest cost |
| Apply quadratic background | 0.45-0.56 s | 0.075-0.086 s | 5.9-6.5x faster |
| Metcalf bilinear translation | 1.84-2.25 s | 0.19-0.22 s | 9.6-10.1x faster |
| Star-aligned zero-shift copy | 0.03 s | avoid the copy | small but free gain |
| Existing mean accumulation | 0.032 s | 0.017 s | 1.9x faster with `where` |

The slice-based translation implements the same bilinear interpolation. Its
largest observed difference from the current implementation was
`8.11e-6 ADU`, attributable to floating-point evaluation order.

The main cause of the current translation cost is rebuilding full-frame X/Y,
floor, neighbour, and validity arrays separately for every RGB channel. A pure
translation has constant fractional weights, so rectangular slices are enough.
The current background application likewise rebuilds a six-plane float64
polynomial grid for every frame. Direct separable evaluation avoids that grid.

## Thread scaling

For four real frames, the optimized background-fit, background-application,
and translation path measured:

| Threads | Wall time | Relative to one thread |
| ---: | ---: | ---: |
| 1 | 1.733 s | 1.00x |
| 2 | 1.059 s | 1.64x |
| 4 | 0.777 s | 2.23x |

NumPy releases the GIL for enough of this work that a bounded thread pool is
effective. Threads are preferable to processes because process IPC would copy
tens of megabytes per frame. Algorithmic optimization must come first: running
the current full-grid implementation concurrently multiplies its large
temporary-array memory demand.

## Current temporary storage

One retained 242-frame work directory contained:

| Generation | Files | Size |
| --- | ---: | ---: |
| Source FITS copies | 247 | 0.95 GiB |
| Siril converted FITS | 247 | 0.95 GiB |
| Preprocessed/debayered RGB FITS | 248 | 5.72 GiB |
| Registered RGB FITS | 243 | 5.61 GiB |
| Total image intermediates | | about 13.23 GiB |

Exact median and rank-fit add two disk-backed float32 cubes, one for the star
stack and one for the Metcalf stack. For this 242-frame RGB size, those cubes
add roughly another 11.2 GiB.

## Recommended implementation order

1. Add stage and per-operation timing counters to the run summary. This makes
   regressions and cold-cache effects visible.
2. Replace pure-translation resampling with the tested slice-based bilinear
   path. Keep the general affine path for SharpCap rotation and future use.
3. Evaluate plane/quadratic background models separably and cache the 1D X/Y
   coordinate vectors per image shape.
4. Accumulate the already star-aligned image directly instead of calling the
   zero-shift resampler. Use `np.add(..., where=mask)` to avoid a full temporary
   product. For mean stacks, reuse the sum count maps as coverage maps.
5. Fuse background fitting and stacking into one registered-FITS pass. Accumulate
   the final RGB background offset statistics and diagnostics as frames pass.
   This removes the second FITS read and enables immediate deletion.
6. Add bounded thread workers, initially 2 by default with an `auto/1/2/4`
   control. Workers should process chunks and return local float64 sums/counts;
   merge chunks deterministically. Select the automatic count from image size
   and available RAM, not CPU count alone.
7. Make cleanup progressive by default. Preserve `--no-cleanup` for diagnosis:
   delete source copies and conversion products after preprocessing is verified;
   delete preprocessed images after registration and reference metadata are
   secured; delete each registered image after its contribution and diagnostics
   have been accepted; delete calibration staging after preprocessing; retain
   logs, sequence metadata, diagnostics CSV, WCS cache, and final products.
8. Prototype Siril `register -2pass`, which officially computes transforms
   without generating transformed images. Parse and validate the full Siril
   matrix, combine star registration and target motion into one resampling of
   each preprocessed frame, and compare against current Siril-registered images.
   If validated, this removes the 5.61-GiB registered generation and one image
   interpolation. It should reduce the measured peak from about 13.23 GiB to
   roughly 7.6 GiB before hard-link savings.
9. Use NTFS hard links for unchanged FITS staging on the same volume, with copy
   fallback across volumes. This avoids the 0.95-GiB physical source duplicate.
10. Add an optional Metcalf-only product mode. It has little benefit for mean,
    but halves the large median/rank-fit disk cube and avoids star/comparison
    FITS outputs when users do not need them.

## Ideas not recommended as first-line changes

- **Only parallelize the current code:** it speeds execution but multiplies
  large per-frame coordinate-grid allocations and can exhaust RAM.
- **ProcessPool/multiprocessing:** serialization and IPC of 25-50 MiB arrays per
  frame are avoidable; measured NumPy threads already scale.
- **Delegate the final Metcalf stack directly to Siril:** Siril can stack an
  existing registered sequence, but its stack command does not accept the
  required independent per-frame target offsets. Pre-shifting files first adds
  another full image generation and I/O pass.
- **FITS gzip/compression for active intermediates:** saves disk at the expense
  of repeated decompression, random-access limitations, and compatibility risk.
- **Store active intermediates as uint16/float16:** this reduces capacity but
  risks clipping signed background-corrected samples or losing photometric
  precision. Keep float32 frames and float64 sums.
- **Input memory mapping as the primary optimization:** FITS endian conversion
  still needs native float data, and measured warm reads are only 0.02-0.07 s
  per frame versus 1.8-2.3 s for current resampling.
- **FITSEQ alone:** it reduces file count and metadata overhead, not the image
  bytes. It may be a later I/O experiment but does not solve peak capacity by
  itself and requires a new Python sequence reader.
- **GPU, CuPy, Numba, or OpenCV first:** they increase package and platform
  complexity. The dependency-free translation prototype already removes most
  of the measured cost.
- **Keep all intermediates as a retry cache by default:** useful only for
  developers and repeated parameter experiments; it conflicts with normal-user
  disk safety. Keep it behind `--no-cleanup` or a future explicit cache option.

## Required validation before production use

- Translation tests for positive/negative integer and fractional shifts,
  mono/RGB data, edge masks, NaN/zero padding, and saturation masks.
- Pixel comparison against the current implementation and photometric aperture
  checks on the comet and reference stars.
- Full 20-frame and 242-frame timing runs in rotated order to control filesystem
  cache effects.
- Thread-count tests under constrained RAM and deterministic float64 reduction.
- Siril matrix convention tests for similarity, affine, and homography before
  removing registered FITS generation.
- Failure-injection tests at every progressive-cleanup boundary.

## Production integration: 2026-08-24

The slice translation, separable background application, direct star
accumulation, `np.add(..., where=...)` mean accumulation, bounded workers,
single-read frame processing, progressive cleanup, and operation timing are now
integrated into the production stack path. The current output canvas remains
the Reference frame footprint.

### Component benchmark after integration

Four retained 220P/McNaught registered RGB frames were measured with a warm
filesystem cache and one timing repeat per frame:

### Correctness

- All four real-frame full valid masks matched the retained legacy algorithm.
- The maximum full-frame pixel difference was `8.10623e-6 ADU`; this comes from
  floating-point evaluation order in the mathematically identical bilinear sum.
- The maximum centre-target aperture difference was `1.06253e-6 ADU`
  (`1.063e-6` relative in the background-subtracted test aperture).
- The maximum automatically selected reference-star aperture difference was
  `1.28994e-6 ADU` (`1.471e-7` relative).
- Unit regressions cover positive and negative shifts, integer and fractional
  shifts, `dx=0`, `dy=0`, mono and RGB arrays, image edges, complete valid masks,
  NaN and zero padding, saturation masks, arbitrary canvas shape/origin, and WCS
  origin rebasing. The full suite passed `154/154` tests on 2026-08-24.

### Production 20-frame wall time

The same 20-frame 220P/McNaught session, cached WCS and ephemeris, Reference
registration, quadratic background correction, and float32 output were run at

| Workers | Stacking wall time | Speedup | Used frames |
| ---: | ---: | ---: | ---: |
| 1 | 12.35 s | 1.00x | 20/20 |

The 1-, 2-, and 4-worker Metcalf float32 FITS arrays were bit-for-bit identical

after enabling early cleanup was bit-for-bit identical to the pre-cleanup
production result, with a maximum difference of `0 ADU` in all three products.

### RAM and temporary allocation impact

For a `3 x 1920 x 1080` frame, a corrected float64 RGB image is about
47.5 MiB, a shifted float32 RGB image about 23.7 MiB, and each 2-D mask about
2.0 MiB. A completed worker result is therefore about 75 MiB with saturation
warnings disabled. During transformation, source data and one bilinear blend
raise the approximate active-worker increment to 110-120 MiB. The two global
float64 sums and two uint32 count maps use about 111 MiB. This gives an
allocation-based estimate of roughly 340 MiB for the main stack arrays at the
then-default two workers, plus Python/FITS/output overhead; four workers add
roughly another 220-240 MiB. These are array-size estimates, not OS peak-RSS
readings. v0.9.0 replaced that fixed default with the RAM-aware selector
described below.

The old quadratic application built six full float64 basis planes (about
95 MiB) plus its correction. Production retains 1-D X/Y terms and only one
temporary full cross-term. The old translation built full X/Y, source
coordinates, four integer-neighbour arrays, and index lists per plane.
Production keeps a small slice plan, one 2-D valid mask, one output plane, and
one blend. No worker owns a full-canvas sum/count accumulator.

This NumPy build links OpenBLAS with up to 24 internal threads. The fitted
least-squares matrices are only about `2500 x 6`, while the dominant elementwise
operations are memory-bandwidth limited. Empirical scaling already flattens at
four workers, so v0.9.0 caps automatic selection at four and uses one or two on
systems whose conservative RAM budget cannot support four.

### Temporary storage and cleanup

Each 20-frame production run removed 80 intermediate FITS files. Its completed
`registration_images` directory retained 26 log/sequence/diagnostic files,
zero FITS files, and 48,006 bytes. Source copies, conversion products, and
staged calibration files are now removed after preprocessing succeeds. The
final preprocessed sequence is removed after registration succeeds; each
registered FITS is removed immediately after its deterministic contribution and
diagnostic row are accepted.

For the retained 242-frame example, removing the 0.95-GiB source-copy and
0.95-GiB conversion generations before registration lowers the estimated
registration peak from about 13.23 GiB to about 11.33 GiB. After registration,
the 5.72-GiB preprocessed generation is removed, leaving the roughly 5.61-GiB
registered generation; that then falls by about 24.9 MB per accepted frame
until zero. Median/rank-fit disk cubes remain unchanged. Removing the remaining
registration peak still requires a separately validated Siril `register -2pass`
matrix path or another registration architecture.

### Expanded-canvas compatibility review

`StackCanvas` expresses output `shape` and `origin` in the independent
registration coordinate system. Slice translation, valid/saturation masks,
accumulator initialization, target output pixels, and FITS `CRPIX` rebasing all
use this object. Production currently selects `StackCanvas.reference_footprint`
as policy, so current dimensions and output remain unchanged. A later N-frame
or percentage-coverage feature can compute another shape/origin and reuse the
same translation path.

The future feature still needs a coverage-policy implementation, output-WCS
tests for each crop/expansion rule, and an explicit decision about preserving
the last source row/column for exact integer translations on a larger canvas.
Those choices were deliberately not folded into this performance change.

### Remaining risks and deferred work

- Filesystem-cache state changes absolute wall times; relative component
  improvements are more stable than one end-to-end run.
- Median and rank-fit still require disk-backed cubes and serial finalization;
  this work primarily improves common mean stacking and shared frame transforms.
- Registration itself and its peak temporary storage remain unchanged. Global
  Registration and Siril `register -2pass` matrix integration remain separate
  future projects.
- GPU/CuPy/Numba, process pools, compressed active FITS, and new dependencies
  remain intentionally excluded. The benchmark evidence does not justify their
  complexity at this stage.

## v0.9.0 automatic workers and 242-frame validation: 2026-08-24

`--stack-workers auto` is now the default. Immediately before starting the
frame pool, production code reads available physical RAM and estimates fixed
stack arrays plus one worker's live arrays from both the registered frame shape
and the independently defined output canvas. It reserves the larger of 512 MiB
or 25% of currently available RAM, then selects the largest fitting count from
4, 2, and 1. An explicit `--stack-workers 1|2|4` remains authoritative.

For the `3 x 1920 x 1080` 220P frames, the conservative estimate was 198.5 MiB
fixed plus 126.7 MiB per worker. Both long runs therefore selected four workers
with a projected 705.4 MiB stack allocation.

| Run | Input/used | Available RAM | Workers | Stack wall | Approx. end-to-end |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 247/242 | 4.34 GiB | 4 | 84.510 s | 397.6 s |
| 2, warm cache | 247/242 | 4.46 GiB | 4 | 73.418 s | 260.8 s |
| Mean | | | | 78.964 s | 329.2 s |

The second stack was 13.1% faster than the first, demonstrating why a single
long-run timing is not sufficient. These stack-only timers must not be compared
directly with the pre-optimization 736.30-second end-to-end benchmark. Repeating
that same full-pipeline benchmark produced 180.131 and 182.808 seconds for
quadratic mode, a mean 4.06x speedup over the old 736.298 seconds. See the
[same-scope end-to-end comparison](../background-normalization-benchmark/RESULTS-20260824-v0.9.0.md).
Detailed stack-only source values and hashes are retained in
[`LONG-RUN-20260824.csv`](LONG-RUN-20260824.csv).

The Metcalf, star-aligned, and side-by-side float32 FITS each had identical
SHA-256 hashes between the two runs. Both runs removed 983 intermediate image
files and completed without an allocation fallback.

### Allocation-failure transaction

Workers still never mutate global sum/count arrays. Production executes a
small batch and does not expose any local result to the main-thread accumulator
until every future in that batch succeeds. If a worker raises `MemoryError`, the
executor cancels pending futures, waits until every running worker has stopped,
breaks traceback references to sibling arrays, and discards the whole
uncommitted batch. The original batch membership is then retried from its first
item at 4 -> 2 -> 1 workers; it is not split into smaller committed subsets when
concurrency drops. Earlier committed batches are not rolled back. The fallback
and currently reported available RAM are logged and stored in the summary JSON.

Failure-injection tests verify that at the fallback callback:

- active worker count is zero;
- no item from the failed batch has been accepted;
- the global accumulator is unchanged;
- successful sibling local results have been released;
- each frame is accepted exactly once after retry;
- 4 -> 2 -> 1 fallback works and one-worker exhaustion becomes a clear error.

Cleanup failure injection separately verifies that the final preprocessed
sequence is never selected for early deletion and that an unlink failure stops
before later candidates. Together with normal success and registration-failure
coverage, this closes the progressive-cleanup validation item identified in the
original analysis.

The RAM calculation is intentionally an allocation estimate rather than an OS
peak-RSS guarantee. Another process can consume memory after selection, which
is why runtime fallback remains necessary. Median/rank-fit finalization and
Siril registration have different memory/disk profiles and remain outside the
frame-worker selector.
