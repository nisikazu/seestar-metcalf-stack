# v0.9.3 registration-matrix and fused-resampling results

This document records the production validation performed on 2026-08-24 for
Siril matrix-only registration and fused star/Metcalf resampling. The benchmark
data is 242 accepted 220P/McNaught S30 frames with fixed ephemeris and WCS so
network and plate-solve latency are outside the measured scope.

## Production path

The normal Siril path now runs `register <sequence>_ -2pass`. Siril detects and
matches stars and writes transformation matrices to the sequence metadata, but
does not write registered `r_*.fit` images. Python converts each Siril
bottom-origin source-to-reference matrix into NumPy array coordinates and
rebases it when Siril's automatic reference differs from the requested
reference.

For the star-fixed product, the source is sampled once with the star matrix. For
the Metcalf product, the target translation is composed as
`T_motion @ H_star`, then the preprocessed source is sampled once with the
combined matrix. Pillow float32 bilinear interpolation is used with an explicit
pixel-centre correction and an independently calculated four-neighbour valid
mask. Pure translations keep the optimized slice path.

The complete SharpCap StackLog transform path remains materialized for now. It
is deliberately separate from this normal Siril path to avoid changing both
registration sources in one release.

## Correctness

The full test suite contains 170 passing tests. Coverage includes:

- Siril-to-array coordinate conversion and reference rebasing
- positive and negative, integer and fractional shifts
- `dx=0` and `dy=0`
- mono and RGB images
- image edges, NaN, zero padding, valid masks, and saturation masks
- output canvases with shape and origin independent from the reference image

The old and new 242-frame products have the same complete 2,073,600-pixel valid
footprint. Exact pixel identity is not expected: v0.9.0 used Siril's default
Lanczos-4 registration followed by a Python bilinear target shift, while v0.9.3
uses one bilinear interpolation.

Single-transform aperture tests against five source-image stars gave these
per-channel mean flux errors:

| Method | R | G | B |
| --- | ---: | ---: | ---: |
| New Pillow bilinear | -0.2167% | +0.0478% | -0.0864% |
| Siril linear | -0.1873% | +0.0748% | -0.0254% |
| Siril cubic | +1.3621% | +2.1007% | +1.6958% |
| Old Siril Lanczos-4 | +0.4450% | +0.9127% | +1.0683% |

The new resampler therefore tracks Siril linear closely and preserves the input
aperture flux better than the old Lanczos-4 stage in this data set.

For the complete old/new Metcalf stacks, a six-pixel target aperture changed by
`-0.2809%, +0.1814%, +0.3687%` in RGB. A ten-pixel aperture changed by
`+0.1795%, -0.0261%, +0.3188%`. A fourteen-pixel aperture was more sensitive
to the selected background annulus and changed by
`-1.2096%, -0.1309%, -1.6607%`. Reference-star centroids moved only about
0.03 to 0.05 pixels. Photometry comparisons must therefore retain the same
aperture and background annulus.

Machine-readable values are in
[`PHOTOMETRY-V093-20260824.csv`](PHOTOMETRY-V093-20260824.csv).

## Performance

All v0.9.3 runs used the same exact 242-frame input, fixed WCS and ephemeris,
`quadratic` background normalization, `mean` stacking, and
`--stack-workers auto`, which selected four workers without fallback.

| Version/run | End-to-end | Registration | Stacking | Peak Python RSS | Temp peak | Registered FITS |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Pre-v0.9 baseline | 736.30 s | not recorded | not recorded | not recorded | about 13.23 GiB | 242 |
| v0.9.0 run 1 | 180.13 s | not recorded | included | not recorded | about 13.23 GiB | 242 |
| v0.9.0 run 2 | 182.81 s | not recorded | included | not recorded | about 13.23 GiB | 242 |
| v0.9.3 run 1 | 174.15 s | 9.85 s | 100.41 s | 1226.4 MiB | 7.48 GiB | 0 |
| v0.9.3 run 2 | 197.60 s | 10.38 s | 111.40 s | 1197.2 MiB | 7.48 GiB | 0 |
| v0.9.3 run 3 | 176.11 s | 10.08 s | 99.38 s | 1231.3 MiB | 7.48 GiB | 0 |

The warm-cache comparison is v0.9.0 run 2 at 182.81 seconds versus v0.9.3 run
3 at 176.11 seconds, a 3.7% end-to-end reduction. Filesystem cache state caused
more variation than this gain, so the result is a modest measured improvement,
not a guaranteed speedup. The primary benefit is storage: 13.23 GiB to
7.48 GiB is a 43.5% reduction, and 242 registered FITS files become zero.

The v0.9.3 process RSS is about 1.20 GiB. v0.9.0 did not record process RSS, so
no direct RAM-reduction claim is made. The raw runs are in
[`LONG-RUN-V093-20260824.csv`](LONG-RUN-V093-20260824.csv).

| After Siril preprocessing | 7.48 GiB | 730 |

| After accepted stack-input cleanup | approximately 0 GiB of image intermediates | metadata only |

The peak still occurs during Siril conversion and preprocessing. Further disk
reduction requires streaming or chunking that stage rather than changing the
stack accumulator.

## Expanded-canvas compatibility

`StackCanvas(shape, origin_x, origin_y)` keeps registration coordinates
separate from output extent. Both general affine and translation paths accept a
source shape and independent output shape/origin. v0.9.3 still emits the
reference-frame footprint, but a future N-frame or M-percent contribution
policy can select a larger canvas without replacing the resampler.

## Remaining risks

- Pillow bilinear and old Lanczos-4 differ intentionally; downstream
  photometry comparisons must not mix versions without noting the resampler.
- The SharpCap StackLog registration path still creates transformed temporary
  images and does not receive the full disk reduction.
- End-to-end timing remains sensitive to Windows filesystem cache and antivirus
  scanning.
- Siril sequence-file matrix conventions are covered by tests and S30 data, but
  future Siril format changes require revalidation.
